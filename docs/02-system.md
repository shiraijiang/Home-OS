# 02 系统结构

本文件只记录已经确认的系统结构，不提前建设复杂架构。

## 当前技术方向

- Google 表格 + Google Apps Script（GAS）。
- 个人家庭系统，不采用 React / FastAPI / PostgreSQL / Docker 等团队级技术栈。
- 先做真实会使用的模块，再从实际使用中扩展数据结构。
- 不建设需要长期人工同步状态的数据系统。

## 首页结构

首页是像素房间。功能通过家具进入，点击后完全换页，不在房间内弹出复杂浮层。

| 家具 | 功能 | 性质 |
|---|---|---|
| 岛台 | 今天吃什么 / 抽卡 | 决策模块 |
| 冰箱 | 私人菜谱库 | 内容参考模块 |
| 吧台 | 记一笔 | 记录模块 |
| 门 | 设置 | 系统模块 |

冰箱作为菜谱入口不会把菜谱系统并入抽卡逻辑；两个模块只共享未来可能需要的轻量接口。

## 吃饭抽卡

职责：减少「今天怎么解决吃饭」的决策成本。

抽卡内容可以覆盖外卖、便利店、超市熟食、微波炉、简单做饭等解决方式。抽到做饭不要求继续访问菜谱，也不以做饭作为更高等级或奖励。

## 私人菜谱库

职责：保存这个家实际会重复使用的做法，解决「上次这个东西怎么做」的问题。

### 录入方式

默认通过 AI 对话产生。只有使用者明确说「存菜谱」时才整理并入库；普通讨论、试验方案和临时想法不自动保存。

### 菜谱定位

面向有做饭经验的人，是参数和操作顺序备忘录，不写教学式常识步骤。重点保存容易忘、实际下厨时需要看的信息。

### 基础格式

每道菜基础字段固定为：

1. **菜名**
2. **份量**
3. **材料**：尽量给具体数量；只有不影响结果时才用「适量」。默认不强制按肉/菜/调味料分组。
4. **容器**：推荐容器种类、数量和大致尺寸/容量，例如 `400ml 饭碗 ×2`、`20×25cm 耐热皿`。
5. **摆放・加工顺序**：只写影响结果的加工先后和空间摆放，例如 `土豆微波 → 洋葱垫底 → 肉铺上层`，不写洗净、切块、倒油等熟手不需要的常识说明。
6. **做法方案**：同一道菜允许保存多个方案，每个方案包含加热参数和风味特点。
7. **换口味**（可选）：只记录相对基础版需要改什么，不复制整份菜谱。
8. **备注**（可选）：只记录踩坑、替代食材等确实值得保留的信息。

不保存难度、星级、营养、收藏、做过次数等维护型字段。

### 做法方案

同一道菜允许存在多个实际会使用的烹饪方案，例如 Bistro 烤箱、Bistro グリル、微波炉、炉灶、高压锅等。不要为了「资料完整」硬补不会使用的方案。

每个方案记录：

- 设备
- 模式
- 温度（适用时）
- 层位（适用时）
- 时间
- 是否预热
- 是否翻面 / 是否需要中途操作
- 风味特点

风味特点只描述最终差异，例如「焦香明显、边缘脆、油脂逼得多」「受热均匀、肉更嫩、焦香适中」，不写「最好吃」之类评价。

### Panasonic Bistro 规则

家中烤箱/蒸烤箱为 Panasonic Bistro。凡使用 Bistro 的方案，必须尽量按照机器实际显示记录：

`设备｜实际模式名｜温度｜第几层｜时间｜预热｜翻面/中途操作`

例如：

`Bistro｜オーブン 予熱あり｜200°C｜下段｜20–25min｜预热｜不翻面`

模式名优先保留机器上的日文名称，不统一改写成泛称「热风」「烧烤」，避免实际操作时二次翻译。使用自动菜单时记录实际菜单名/编号及层位。

### 换口味

换口味是基础菜谱上的小改动，例如：

- 韩式：基础酱汁 → 韩式辣酱 + 少量糖，出炉撒芝麻
- 蒜香：增加蒜末，最后阶段刷蒜油
- 日式：酱油 + 味醂，出炉加七味粉

只写差异；如果容器、摆放和加热参数不变，不重复。

### 三种可叠加模式

模式是对基础菜谱的调整，不复制成另一份完整菜谱；可组合使用。

**懒人模式：目标是省力。**

- 优先减少切配、锅具、清洗、翻面和中途操作。
- 可以接受总耗时稍长。
- 优先微波炉、Bistro 一锅出、锡纸/烘焙纸等减少清洗的方案。
- 给出明确容器、摆放顺序和加热参数。

**极速模式：目标是最快吃上饭。**

- 以实际从开始做到能吃的总耗时为准。
- 可以接受多一个锅或多一步，只要明显缩短总时间。
- 允许微波预处理 + 煎/烤等组合。
- 设备时间必须考虑预热、升压、泄压等等待时间，不能只比较机器标称加热时间。

**清淡模式：目标是调整风味和烹调负担。**

- 根据菜品实际情况减少油脂、刺激性、过重调味或焦化程度。
- 必要时可以替换食材或改变烹调方式，而不是机械地只减盐。
- 只记录相对基础版的变化。

### 高压锅规则

家中有高压锅，但清洗成本高。因此：

- 普通方案：仅在炖肉、牛筋、猪蹄、豆类等优势明显的菜中优先考虑。
- 懒人模式：原则上排除高压锅，因为清洗也是劳动量。
- 极速模式：可以使用，但必须把升压和泄压时间计入总时间。
- 如果高压锅能明显减少看火或长时间炖煮，可作为备选方案并注明风味特点。

设备推荐评价的是完整成本：准备 + 操作 + 等待 + 清洗，而不是单看机器运行时间。

## 抽卡与菜谱的关系

两者互不依赖：

- 没有任何菜谱，抽卡仍能正常工作。
- 不使用抽卡，菜谱仍然可以独立查阅。
- 未来允许弱关联，例如抽到「做饭」后由系统推荐一个符合当天档位的菜。
- 弱关联不得演变成库存匹配、营养计算或复杂推荐引擎。

## 数据原则

- 一天只输入一次「档位 + 要不要肉」，需要该信息的模块可以共用。
- 流水表保持肉眼可读；现有决定为七列固定，额外需求优先独立小表，不使用 JSON 扩展列。
- 内容可以由使用者自行修改；新增模块不要求建设通用可视化搭建器。
- 菜谱是静态/低频内容，不属于需要每天同步状态的数据。
- 菜谱可以逐渐增加，但不要求为了系统完整性批量录入；只在实际出现值得保留的做法时加入。
