# 02 系统结构

本文件只记录已经确认的系统结构，不提前建设复杂架构。

## 当前技术方向

- Google 表格 + Google Apps Script（GAS）。
- 个人家庭系统，不采用 React / FastAPI / PostgreSQL / Docker 等团队级技术栈。
- 先做真实会使用的模块，再从实际使用中扩展数据结构。
- 不建设需要长期人工同步状态的数据系统。

## 首页结构

首页是像素房间。功能通过家具进入，点击后完全换页，不在房间内弹出复杂浮层。

| 家具 | 功能 | 性质 |
|---|---|---|
| 岛台 | 今天吃什么 / 抽卡 | 决策模块 |
| 冰箱 | 私人菜谱库 | 内容参考模块 |
| 吧台 | 记一笔 | 记录模块 |
| 门 | 设置 | 系统模块 |

冰箱作为菜谱入口不会把菜谱系统并入抽卡逻辑；两个模块只共享未来可能需要的轻量接口。

## 吃饭抽卡

职责：减少「今天怎么解决吃饭」的决策成本。

抽卡内容可以覆盖外卖、便利店、超市熟食、微波炉、简单做饭等解决方式。抽到做饭不要求继续访问菜谱，也不以做饭作为更高等级或奖励。

## 私人菜谱库

职责：保存这个家实际会重复使用的做法，解决「上次这个东西怎么做」的问题。

第一版菜谱内容保持简单：

- 菜名
- 份量
- 材料
- 做法
- 设备 / 时间
- 备注

不建立库存、营养、评分、复杂标签、完成记录等维护型字段。

菜谱可以逐渐增加，但不要求为了系统完整性批量录入。只在实际出现值得保留的做法时加入。

## 抽卡与菜谱的关系

两者互不依赖：

- 没有任何菜谱，抽卡仍能正常工作。
- 不使用抽卡，菜谱仍然可以独立查阅。
- 未来允许弱关联，例如抽到「做饭」后由系统推荐一个符合当天档位的菜。
- 弱关联不得演变成库存匹配、营养计算或复杂推荐引擎。

## 数据原则

- 一天只输入一次「档位 + 要不要肉」，需要该信息的模块可以共用。
- 流水表保持肉眼可读；现有决定为七列固定，额外需求优先独立小表，不使用 JSON 扩展列。
- 内容可以由使用者自行修改；新增模块不要求建设通用可视化搭建器。
- 菜谱是静态/低频内容，不属于需要每天同步状态的数据。

具体实现字段可在开发菜谱模块时根据真实样本微调，不提前扩展为大型数据模型。
