# 05 决定日志

**只追加，不修改。** 已定的事不要重新讨论。有异议先说明理由，由使用者拍板。

格式：`日期 | 决定 | 理由`

> 这份文件是历史轨迹，不是现行规格。编号大的覆盖编号小的，旧条目即使失效也留在原位。
> **理由栏记录的是当初为什么这么定，任何情况下都不得改写或替换**——要表达覆盖关系，只能新增编号，或在原理由后括注。
> 要知道「现在按哪条做」：范围看 `01-spec.md`，系统看 `02-system.md`，交互看 `03-interaction.md`，美术看 `04-art.md`。

## 2026-08 方向

| # | 决定 | 理由 |
|---|---|---|
| 1 | 技术栈用 Google 表格 + GAS，不用 React/FastAPI/PostgreSQL/Docker | 个人项目，团队级技术栈会死在环境配置上 |
| 2 | 先做一个真的会打开的模块，让数据结构从使用里长出来；不先建抽象数据中台 | 提前抽象出来的中台，最后一定跟真实用法对不上 |
| 3 | 砍掉菜谱、食材、库存、营养、成员偏好 | 使用者九成买来吃；且这些都要求持续喂数据。（其中「完全砍掉菜谱」已被 #50～#53 覆盖） |
| 4 | 凡是需要定期手动同步状态的功能一律不做 | 生死线。破一次，三个月内必死 |
| 5 | 一天只输入一次「档位 + 要不要肉」 | 减少重复决策唯一真正起作用的地方 |
| 6 | 做饭是 3 档里的一个正常选项，不是升级目标 | 避免「今天又没做饭」的隐性负担 |
| 7 | 抽牌只给一个答案，不给列表 | 给列表等于把决策还给人 |

## 2026-08-11 菜谱模块调整

| # | 决定 | 理由 |
|---|---|---|
| 50 | 「今天吃什么」抽卡与私人菜谱库拆成两个独立模块 | 一个负责做决定，一个负责查家庭做法，避免牌池和资料库互相拖累 |
| 51 | 岛台继续作为吃饭抽卡入口 | 保留原有空间语义和交互 |
| 52 | 冰箱作为私人菜谱库入口 | 厨房语义自然，也不需要增加新的大型家具 |
| 53 | 恢复轻量私人菜谱库，但不恢复菜谱管理系统；不做库存、营养、评分、复杂标签和持续维护流程 | 允许保存实际会重复使用的家庭做法，同时控制维护成本；覆盖 #3 中「完全砍掉菜谱」 |
| 54 | 抽卡和菜谱互不依赖，未来只允许弱关联，例如抽到做饭后给一个菜谱建议 | 保持模块独立，避免提前建设复杂推荐系统 |
| 55 | 菜谱默认通过 AI 对话录入；只有使用者明确说「存菜谱」才整理入库 | 避免试验方案和随口讨论污染菜谱库 |
| 56 | 菜谱采用熟手备忘格式：菜名、份量、材料、容器、摆放/加工顺序、做法方案、可选换口味、可选备注 | 做饭时主要需要参数和顺序，不需要教学式步骤 |
| 57 | 同一道菜允许多个做法方案；每个方案保存加热参数和简短风味特点 | 不同设备/做法的价值在于操作和最终风味差异 |
| 58 | Bistro 方案必须尽量记录机器实际模式名、温度、层位、时间、预热和翻面/中途操作；模式名优先保留日文 | 可以直接照机器操作，避免二次翻译和遗漏关键参数 |
| 59 | 「换口味」只保存相对基础版的差异，不复制整份菜谱 | 保持资料轻量，减少重复维护 |
| 60 | 菜谱支持可叠加的「懒人模式 / 极速模式 / 清淡模式」 | 分别优化省力、最快吃上饭、清淡调整，目标不同不能混为一个模式 |
| 61 | 懒人模式优先减少切配、锅具、清洗、翻面和中途操作，允许总耗时稍长 | 评价的是人的劳动量，不只是烹饪时间 |
| 62 | 极速模式按实际开做到能吃的总时间判断，可接受多一步/多设备；预热、升压、泄压等必须计时 | 防止把机器运行时间误当成真实最快方案 |
| 63 | 清淡模式可调整油脂、刺激性、调味、焦化程度、食材或烹调方式，不机械等同于少盐 | 不同菜的清淡化方法不同 |
| 64 | 高压锅属于高清洗成本设备；懒人模式原则上排除，普通模式仅在优势明显时优先，极速模式必须计入升压和泄压 | 设备成本按准备、操作、等待和清洗全过程计算 |
