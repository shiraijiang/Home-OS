# 01 规格：目标、原则、范围

## 目标

减少生活里的重复决策，减少能量损耗。

追求高质量，但**允许为了节能主动降低标准或优先级**——降级是系统内置的正常动作，不是失败。

## 使用者

一个人使用。不做多人协作、不做同步、不做家庭成员偏好平衡。

## 核心原则

### 一、凡是需要定期手动同步状态的功能，一律不做

这是生死线。库存、体重、待办清单、预算余额、读书进度、习惯打卡——全部不做。这类功能要求人持续喂数据，系统容易因维护负担被弃用。

需要的信息一律靠**被动记录**或**一次性输入**积累，让系统去读，不让人去维护。

### 二、输入收口

一天只回答一次「今天几档 + 要不要肉」，需要这个信息的模块共用结果。

### 三、永远做选择题，不做填空题

认出来比想出来省力。系统出初稿，人只做删除和调整。

### 四、不制造心理负担

- 不做连续打卡、不做进度条、不做成就任务
- 不做「今天没完成」的红点
- 不做需要照顾的养成对象
- 偶发内容只在打开的瞬间掷骰子，不制造停留压力

## 第一版核心入口

| 入口 | 家具 | 功能 |
|---|---|---|
| 吃 | 岛台 | 抽卡决定今天怎么解决吃饭 |
| 记一笔 | 吧台 | 随手记录 |
| 设置 | 门 | 拼卡片、改牌堆、锁定季节与光 |

## 独立内容模块：私人菜谱库

菜谱与「今天吃什么」抽卡系统分离。

- 抽卡负责**做决定**：今天通过外卖、便利店、超市熟食、微波炉、简单做饭等哪种方式解决。
- 菜谱负责**保存家庭实际会重复使用的做法**：例如具体份量、材料、步骤、设备和个人备注。
- 菜谱入口使用**冰箱**。
- 菜谱库不依赖抽卡；抽卡也不依赖菜谱库。
- 未来可以做弱关联，例如抽到「做饭」后给出一个适合当前档位的菜，但不是第一版的依赖关系。
- 不做菜谱评分、营养计算、库存联动、复杂标签和需要持续整理的管理流程。

这项决定覆盖旧规则中「完全不做菜谱」的部分。仍然不做的是**需要持续维护的菜谱管理系统**。

## 明确不做

- 食材表、冰箱库存管理、营养计算
- 需要持续维护的菜谱管理系统
- 家庭成员偏好系统、评分系统
- 记账明细、体重日记、待办清单、习惯打卡
- 社区、分享、多人功能
- 任何需要人工持续维护状态的东西

## 吃饭模块边界

使用者多数时候通过购买解决吃饭，因此抽卡首先解决「今天用什么方式、买什么」的重复决策。做饭是其中一个正常选项，不是升级目标，不催、不奖励、不记录完成率。

私人菜谱库是独立的长期参考资料，不承担库存管理或每日决策职责。
